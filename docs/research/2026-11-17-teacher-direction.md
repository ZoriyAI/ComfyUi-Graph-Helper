# NodeWise for teachers: product direction and delivery contract

Research date: 17 November 2026. The owner's starting example is a primary-school teacher expected to adopt modern tools without practical support. This is a qualitative discovery signal, not established market demand.

The proposed promise is: **prepare useful classroom materials, understand the suggestions, and choose what to use**. The first result must not require node knowledge, ComfyUI, a paid model or pupil accounts. The existing NodeWise lesson format teaches graph construction; a classroom resource is a separate product object.

## Evidence and implications

- [OECD TALIS 2024](https://www.oecd.org/en/publications/results-from-talis-2024_90df6235-en/full-report/teaching-for-today-s-world_eefb146b.html) identifies skill barriers among teachers not using AI. Guided practice is a product hypothesis; this international survey does not establish demand in Russian primary schools.
- [EEF's trial](https://educationendowmentfoundation.org.uk/news/teachers-using-chatgpt-alongside-a-guide-to-support-them-to-use-it-effectively-can-cut-lesson-planning-time-by-over-30-per-cent) involved 259 teachers across 68 English secondary schools. ChatGPT with guidance reduced Year 7–8 science planning time by 31% on average; a reviewed sample showed no noticeable quality difference. These findings do not establish NodeWise's effectiveness or improved pupil learning.
- [UNESCO's teacher competency framework](https://www.unesco.org/en/articles/ai-competency-framework-teachers?hub=779) supports teacher agency and progressive competence. Keep choices and explanations visible.
- [Oak's Aila guide](https://support.thenational.academy/using-aila) demonstrates staged review, editable export and sharing. At the research date it did not generate images/diagrams; its [FAQ](https://support.thenational.academy/aila-faqs) did not support mobile use. These are current observations of one product, not permanent competitive claims.
- [CAST UDL](https://udlguidelines.cast.org/representation/language-symbols/multiple-media/) supports alternative ways to represent concepts. Offer text, illustration and practical activity without assigning children fixed learning styles.
- [EEF on individualised instruction](https://educationendowmentfoundation.org.uk/education-evidence/teaching-learning-toolkit/individualised-instruction) notes organisational demands. Start with a small number of variants sharing the same objective.
- [DfE support materials](https://www.gov.uk/government/collections/using-ai-in-education-settings-support-materials) provide another example of progressive staff support, not a regulatory requirement for other countries.

## Ten design perspectives

1. Tomorrow's lesson: deliver one usable small resource before a complete course.
2. A first-time AI user: ask topic, age/class, objective and result type with examples.
3. An experienced teacher: preserve existing materials, edit a selected block and compare versions.
4. A pupil in class: separate the learning goal from decoration; keep answers and teacher notes separate.
5. A diverse class: offer scaffolded, independent and extension variants, readable layout and alternative descriptions.
6. A real school computer: manual editing and saved resources work without a GPU; generation needs an explained host assessment.
7. Interrupted work: retain completed blocks, report the cause and retry only the failed step.
8. A receiving colleague: ordinary output opens without NodeWise; regeneration dependencies belong to the editable project.
9. A methodologist: authorship, sources, versions and peer review precede a complex administration platform.
10. Distribution and investment: measure accepted resources, repeat use, successful handoffs, support and actual operating costs.

## First path and architecture

Choose classroom materials → select cards, worksheet, questions, explanation plan, storyboard or support variants → supply topic/class/objective and optional source text → open a manual scaffold or request a configured assistant draft → edit individual blocks → preview pupil output → save ordinary output and an editable copy → reopen and adapt.

Do not force a complete lesson plan to obtain three cards. Advanced generation parameters appear only when relevant. A classroom material has a versioned format, stable block ids, separate teacher notes/answers, language, objective, sources and provenance. Text remains text; renderers escape content and do not execute imported scripts or silently fetch external resources. Student export omits teacher data entirely, including hidden HTML. A real print/PDF path must be verified; an HTML file is not a PDF.

One material-type registry drives the wizard, agent and import validation. The existing `draftLesson` remains for graph lessons; classroom materials require a separate typed draft capability. A draft is not pedagogical validation. Counting and geometry require deterministic data; a generated picture is not a verified scientific diagram. Remote browser diagnostics describe the NodeWise host.

Use existing seams: `TaskWizard.tsx` for workflow handoff, `shared/templates/catalog.ts` for native workflows, `main/agent/tools.ts` for assistant drafting, `components/journey` for first start, `main/comfy/hardware.ts` and `main/knowledge/resources.ts` for hardware/resource explanation. Keep classroom material storage distinct from node-learning lessons and publish only intentionally shared content.

| EDU-09 | Teacher pilot | Real adult participants, correction time and observed completion |
| EDU-10 | Public catalogue | Author-initiated publication, provenance/version/dependencies/download |

All gates remain open until their evidence exists. Finish the MCP hotfix release first; then EDU-01–03 with standalone host diagnostics, print/accessibility, generation, sharing and pilot. A feature catalogue alone closes none of these gates.

## Pilot and distribution

Proposed pilot: 8–12 adult primary teachers, including AI beginners and weak-computer users. Compare their usual method with NodeWise on comparable cards, source-based worksheets and support variants, alternate task order and record assistance. Include one colleague handoff. Participants have not been recruited; no invitations are sent without instruction.

Measure time to a teacher-accepted artifact including review/corrections; independent completion; factual accuracy, age suitability, clarity and objective fit; repeat use at 7/28 days; successful colleague adaptation; corrections; support minutes and real provider costs per accepted material. Proposed internal thresholds are 80% independent completion, median small-resource completion within 10 minutes, no lost work or answer leakage, and 80% teacher acceptance after reasonable editing. These are hypotheses to test, not marketing claims or proof of pupil learning.

The distribution hypothesis is useful resource → colleague handoff → adaptation → own resource → another handoff. Let ordinary files open before installation and keep optional attribution unobtrusive. Portal task pages should show reproducible examples and honest readiness. Investor evidence should cover active creators, accepted resources, repeat use, successful sharing, support costs, generation costs and actual school interest. Downloads, templates and an acquaintance's audience are not revenue or retention.

Later business hypotheses include school support, shared libraries, managed servers, reviewed subject packs and methodologist training. Pricing and commercial decisions remain separate owner decisions. Do not block essential export or accessibility before demonstrating basic value.

No claim that everyone can use the product follows from a developer's walkthrough: first-time teachers must actually try it.

## First implementation and verification — 17 November 2026

- Code implements six text material types, wizard, block editing, separate answer fields, preview, a local draft, JSON import/export and pupil/teacher HTML. Entry points exist on the welcome screen and Help menu; RU/EN help is written.
- Actual isolated Electron: Russian empty-start, export, reload, invalid/valid import passed. Chromium generated a PDF from the exported sheet. No physical printer was tested.
- A separately paired browser with390px touch emulation imported an English desktop file through its file picker, edited and downloaded it; the desktop original stayed unchanged. This is functional browser evidence, not physical Android/iOS acceptance.
- The actual configured local Qwen3.8-27B produced3valid addition questions with answers5,5,6. The editor kept existing work until explicit acceptance, and the graph stayed unchanged. The first attempt ended after reasoning-only data; the quick drafting request toOllama repaired this particular journey(27s). Service settings were unchanged; this does not prove universal model reliability.
- EDU-01 and the technical part ofEDU-03 are verified within those boundaries. EDU-02: wizard drafting passed, individual block operations/version comparisons remain unimplemented. EDU-04: HTML→PDF passed, physical printing/all layouts remain. EDU-07: cross-device transfer passed, an independent colleague has not participated. EDU-05/06/09/10 remain later deliveries; EDU-08 needs broader accessibility qualification.
- This is a foundation, not completion of all60scenarios. Exercise collections, exact counting/geometry, illustrations, shared libraries, the public catalog and educator pilot are not claimed ready.
